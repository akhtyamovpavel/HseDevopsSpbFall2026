# Справочник основных команд Git (локальная работа)

В данном документе собраны базовые команды Git для локальной работы с репозиторием (до команд удалённого взаимодействия `push`, `pull`, `fetch`).

---

## 1. Первоначальная настройка (Configuration)

В Git существует три уровня конфигурации:
* `--system` — для всех пользователей операционной системы.
* `--global` — для текущего пользователя ОС (действует на все его репозитории по умолчанию).
* `--local` (по умолчанию) — действует только в рамках текущего репозитория.

> [!WARNING]
> **Почему `git config --global user.name ...` — плохой паттерн?**
> 1. **Смешение контекстов (учёба / работа / личные проекты):** если вы работаете с несколькими профилями или аккаунтами на одной машине (например, корпоративный GitLab, рабочий аккаунт, учебный GitHub в ВШЭ или личные pet-проекты), глобальная конфигурация приведёт к тому, что коммиты будут ошибочно подписываться чужим именем или почтой.
> 2. **Утечка приватных данных:** из-за глобальной настройки можно случайно закоммитить личную или корпоративную почту в публичный репозиторий.
> 3. **Кодировка и язык:** в `user.name` не рекомендуется использовать кириллицу (например, `"Ваше Имя"`). Имя лучше писать латиницей (например, `"Ivan Ivanov"`), чтобы избежать проблем с кодировками в сторонних утилитах, терминалах, git-хуках и CI/CD пайплайнах.
>
> **Рекомендуемый паттерн:** настраивать имя и почту **локально** под каждый конкретный проект с помощью `git config` (или `git config --local`), либо настраивать секции `[includeIf]` в файле `~/.gitconfig` в зависимости от пути к папке с проектом.

```bash
# Локальная настройка для текущего репозитория (РЕКОМЕНДУЕТСЯ)
git config user.name "Ivan Ivanov"
git config user.email "iivanov@edu.hse.ru"

# Глобальная настройка (только если все репозитории на машине относятся к единственному профилю)
git config --global user.name "Ivan Ivanov"
git config --global user.email "iivanov@example.com"

# Просмотр всех действующих настроек с указанием файла-источника
git config --list --show-origin
```

## 2. Инициализация репозитория (Initialization)

```bash
# Инициализация нового Git-репозитория в текущей директории (создаёт служебную папку .git)
git init
```

---

## 3. Статус и просмотр изменений (Status & Diff)

```bash
# Проверка текущего состояния репозитория (изменённые, новые и проиндексированные файлы)
git status

# Просмотр разницы (diff) для изменённых, но ещё не добавленных в индекс файлов
git diff

# Просмотр изменений, которые уже добавлены в индекс и войдут в следующий коммит
git diff --staged
# или аналогичная команда:
git diff --cached
```

---

## 4. Индексация и создание коммитов (Staging & Commits)

```bash
# Добавить конкретный файл в индекс (Staging Area)
git add <имя_файла>

# Добавить все изменённые и новые файлы в текущей директории в индекс
git add .

# Убрать файл из индекса и перестать отслеживать, сохранив его на диске
git rm --cached <имя_файла>

# Зафиксировать проиндексированные изменения (создать коммит) с сообщением
git commit -m "Понятное описание сделанных изменений"

# Добавить все отслеживаемые изменённые файлы в индекс и сразу закоммитить
git commit -am "Описание изменений"

# Дополнить последний коммит (добавить забытые файлы или изменить сообщение)
git commit --amend
```

> [!WARNING]
> **Почему `git commit -am` нельзя делать, если есть лишние файлы / изменения:**
> 1. **Захват лишних изменений:** флаг `-a` автоматически добавляет в коммит **все** изменённые отслеживаемые файлы. Если вы параллельно правили несколько файлов, оставили отладочные принты, временные конфиги или незавершённые правки — они все без проверки попадут в историю проекта.
> 2. **Игнорирование новых файлов:** флаг `-a` захватывает только *уже отслеживаемые* (tracked) файлы. Новые созданные файлы (untracked) **не попадут** в коммит, из-за чего коммит окажется неполным, а сборка или тесты сломаются.
> 3. **Нарушение атомарности коммитов:** коммит должен содержать одно логически завершённое изменение. Команда `-am` провоцирует сваливать всё подряд в один коммит.
>
> **Правильный паттерн:**
> 1. Проверить состояние: `git status`
> 2. Посмотреть изменения: `git diff`
> 3. Осознанно добавить только нужные файлы: `git add <файл1> <файл2>` (или построчно: `git add -p`)
> 4. Создать коммит: `git commit -m "Конкретное сообщение"`

## 5. Просмотр истории (History / Log)

```bash
# Стандартный просмотр истории коммитов
git log

# Компактный вывод истории (каждый коммит в одну строку)
git log --oneline

# Наглядное отображение истории в виде псевдографического дерева со всеми ветками
git log --graph --oneline --all

# Просмотр подробной информации и diff конкретного коммита
git show <хэш_коммита>
```

---

## 6. Работа с ветками (Branches)

```bash
# Список локальных веток (звёздочкой * помечена текущая)
git branch

# Создать новую ветку с указанным именем
git branch <имя_ветки>

# Удалить ветку (безопасное удаление: только если ветка уже слита)
git branch -d <имя_ветки>

# Принудительно удалить ветку (даже если есть неслитые коммиты)
git branch -D <имя_ветки>
```

## 7. Переключение между ветками (Switch & Checkout)

```bash
# Переключиться на существующую ветку (современная команда)
git switch <имя_ветки>
# или классическая команда:
git checkout <имя_ветки>

# Создать новую ветку и сразу переключиться на неё
git switch -c <имя_ветки>
# или классическая команда:
git checkout -b <имя_ветки>

# Создать новую ветку от конкретной базовой ветки и переключиться (РЕКОМЕНДУЕТСЯ)
git switch -c <имя_новой_ветки> <базовая_ветка>
```

> [!WARNING]
> **Минусы команды создания и одновременного переключения (`git switch -c` / `git checkout -b`):**
> 1. **Неявная точка отсчёта (ветвление «не оттуда»):**
>    Команда по умолчанию создаёт новую ветку от текущего `HEAD`. Если разработчик забыл проверить текущую ветку (например, находился в другой незавершённой feature-ветке, а не в чистом `main`), новая ветка унаследует чужие черновые коммиты и историю.
> 2. **Неявный перенос «грязного» рабочего состояния (uncommitted changes):**
>    Если в рабочей директории или индексе были незакоммиченные изменения, Git перенесёт их в новую ветку. Если эти изменения относились к старой ветке, вы рискуете закоммитить их в новую по ошибке.
> 3. **Создание ветки от устаревшей локальной базы:**
>    Создавая ветку «на лету» от текущего состояния, легко забыть предварительно синхронизировать базовую ветку.
> 4. **Перегруженность классической `git checkout`:**
>    Историческая команда `git checkout` совмещает слишком много разных задач: переключение веток, создание веток (`-b`), откат файлов (`git checkout -- <file>`), переход в состояние `detached HEAD`. Случайная опечатка в имени ветки могла привести к потере незакоммиченных изменений в одноимённом файле. Поэтому в Git 2.23+ её разделили на узкоспециализированные `git switch` (для веток) и `git restore` (для файлов).
>
> **Безопасная практика:**
> 1. Проверить чистоту рабочего каталога: `git status`.
> 2. Переключиться на целевую ветку-основу: `git switch main`.
> 3. Создать ветку с явным указанием базы: `git switch -c <имя_ветки> main`.

## 8. Слияние веток и разрешение конфликтов (Merge)

```bash
# Слить указанную ветку в текущую активную ветку
git merge <имя_ветки>

# Прервать процесс слияния при конфликте и вернуть всё как было
git merge --abort
```

### Разрешение конфликтов при слиянии:
1. Если одни и те же строки были изменены по-разному в обеих ветках, Git отметит конфликт маркерами:
   ```text
   <<<<<<< HEAD (текущая ветка)
   Ваши изменения
   =======
   Изменения из вливаемой ветки
   >>>>>>> <имя_ветки>
   ```
2. Откройте конфликтующие файлы в редакторе, выберите нужный вариант и удалите маркеры конфликта.
3. Пометьте конфликт как разрешённый, добавив файл в индекс:
   ```bash
   git add <имя_файла>
   ```
4. Завершите слияние созданием коммита:
   ```bash
   git commit
   ```

## 9. Отмена изменений (Undoing Changes)

```bash
# Отменить незакоммиченные изменения в файле рабочей директории
git restore <имя_файла>
# или классическая команда:
git checkout -- <имя_файла>

# Убрать файл из индекса (Staging Area), сохранив изменения в самом файле
git restore --staged <имя_файла>
# или классическая команда:
git reset HEAD <имя_файла>
```
